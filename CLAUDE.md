# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

A three-stage Python pipeline that finds restaurants in Medellín / Oriente Antioqueño from OpenStreetMap, audits their web presence, and ranks them by a "Sell Score" as leads for web design + digital menu + SEO services, plus a local web app (`app.py`, `server/`, `ui/`) to read the leads and drive the pipeline. No API keys required (`GOOGLE_API_KEY` is optional and only raises PageSpeed rate limits). The offline scrape/closed-place tests live in `tests/` (`python -m unittest discover -s tests`; no browser or network needed); there is no linter, and the root is not a git repo (the `ui/` scaffold created its own `.git`).

## Layout

- Root: thin entry points only (`app.py`, `discover.py`, `audit.py`, `score.py`, `quality.py`, `enrich.py`, `ingest.py`, `approve.py`, `scrape.py`). Each is a two-line `runpy` wrapper around a module in `leadgen/`, so `python audit.py ...` and the server's subprocess calls (`python("audit.py")`) keep working. Edit the module, not the wrapper.
- `leadgen/` is the pipeline package: `config.py`, `store.py`, then one subpackage per stage: `discovery/` (discover), `audit/` (audit, urlcheck, sitesignals, sitefind), `scoring/` (score, quality), `enrichment/` (enrich, ingest, llm, research, scrape, approve). Import as `from leadgen.audit import urlcheck`, never bare `import urlcheck`.
- `data/` is everything generated and git-ignored: `leads.db`, `leads/<slug>/`, `runs/<job>/`, `exports/*.csv`, `backups/`. Paths come from `config.DATA_DIR`; nothing should hard-code them.
- `server/` (Starlette API) and `ui/` (Vite + React) are unchanged. `PRODUCT.md` / `DESIGN.md` stay in the root because the design skills read them there.

## Commands

```
pip install -r requirements.txt
python discover.py laureles        # OSM/Overpass -> leads.db (table `places`); no args = config.DEFAULT_AREAS; any key of config.ALL_AREAS works
python audit.py [--refresh] [--only PLACE_ID]   # audits places not yet in `audits` + rechecks broken URLs; writes `audits`, `url_checks`
python audit.py --discover   # also look for websites of "no website" places (guessed domains, strictly verified; table `url_discovery`)
python audit.py --perf       # fill missing PageSpeed scores later (free API 429s; GOOGLE_API_KEY helps)
python audit.py --rescore    # offline: recompute web_score + confidence from stored audits (run after changing scoring)
python score.py [out.csv]   # reads places+audits, writes ranked CSV (default data/exports/leads_ranked.csv)

python app.py [--no-browser]       # web app on http://127.0.0.1:<config.UI_PORT>; serves ui/dist
npm --prefix ui run build          # tsc -b && vite build (this is also the type check); run after any change in ui/
npm --prefix ui run dev            # Vite dev server on config.UI_DEV_PORT, proxying /api to app.py
```

The stages must run in order and communicate only through the SQLite file `data/leads.db` (path in `config.DB_PATH`, relative to the cwd).

No-API-key path (the user has Claude Max only, no API key): `python enrich.py --collect-only --only NAME` writes `data/leads/<slug>/context.md` + `schemas.json` with no LLM calls; the analysis is then done by Claude Code in-session (read context.md, view the photos/menu files, use WebSearch/WebFetch for reviews/Instagram/TripAdvisor/closure signals), saved as `data/leads/<slug>/profile/profile.json` (optionally `menu.json`, `presence.json`, `design_system.json`, validated against `llm.*_SCHEMA`), and `python ingest.py NAME` records it via `enrich.finish()`. Still ask the user before analyzing each lead.

Optional keyless scrape of the lead's public Google Maps listing + Instagram profile: `python enrich.py --collect-only --scrape [maps,instagram] --only NAME` (or the "Read their public pages" panel on a lead's Materials tab, `POST /api/leads/<key>/scrape` on the `pipeline` lane, or the checkbox in the Get insights popover, or `python scrape.py NAME [--only maps|instagram] [--headed]`). Needs `pip install playwright && python -m playwright install chromium`. `scrape.py` drives headless Chromium logged out, never logs in or tries to pass a login wall/captcha/429 (the source is recorded `blocked`); Maps works (rating, review count, closed flag, reviews, photos, only kept when the listing name matches), Instagram mostly returns `blocked` for logged-out visitors. Results: `profile/scrape.json`, a "Scraped public pages" section in `context.md`, photos as `photos/{maps,instagram}/scrape-NN.jpg` (replaced on each scrape, user drop-ins untouched). Both sites forbid scraping in their terms; it stays opt-in and one lead at a time. Selectors are fragile; fix them in `scrape.py` when Maps changes.

Per-lead enrichment (needs `ANTHROPIC_API_KEY`, read from the environment or a git-ignored `.env` loaded by `config.load_env()`; real env vars win):
```
python approve.py approved <name-or-place_id> ...   # also: enriched|ready|contacted|rejected, `list [status]`
python enrich.py [--only NAME] [--refresh] [--no-research]   # approved leads -> profile in lead_profile, status enriched
```

## Architecture

- `config.py` — single source of tuning: `ALL_AREAS` (center lat/lng/radius for every known area), `DEFAULT_AREAS` and the derived `AREAS` (what a bare `discover.py` covers), score `WEIGHTS` (need/ability/momentum/reach, sum 100), `CHAINS` and `SOCIAL_DOMAINS` lists, request delay/user agent.
- `discover.py` — Overpass query for `amenity=restaurant` around each area, with fallback across mirrors. Rows are keyed `osm:<type>/<id>` and inserted with `INSERT OR REPLACE`. The full OSM tag dict is stored in `tags_json`, which `score.py` relies on. If a place has no website but has an Instagram/Facebook tag, that social URL is stored in `website` so `audit.py` classifies it as `social_only`.
- `urlcheck.py` — `check()` health-checks a website URL (variants: www, http/https, root; browser UA) -> `ok|parked|blocked|dead|unreachable` plus `name_match`; persisted in table `url_checks`.
- `audit.py` — `classify()` buckets each URL as `none` / `social_only` / `website`; real websites go through `urlcheck.check()` first, and only `ok` ones are fetched, HTML-heuristic checked, and run through the free PageSpeed API (skipped for the run after repeated 429s). `web_score()` yields 0–100 (higher = better site); `none` and `social_only` score 0.
- `score.py` — Sell Score = need (inverse of web score) + ability + momentum + reach, then tier A/B/C. Exclusions (chains, non-operational, Maps-confirmed `permanently closed` via `place_quality`, etc.) are applied before scoring; `excluded(p, maps)` takes the optional `place_quality` row. `ranked(con, include_excluded)` returns the row dicts (the CSV's `CSV_FIELDS` plus extras such as `reasons`); both `main()` and the web app use it, so the CSV and the app cannot drift.
- `approve.py` / `enrich.py` / `llm.py` / `store.py` — per-lead pipeline run only on leads with `lead_status = 'approved'`. `enrich.py` crawls the lead's own site, reads photos you drop into `data/leads/<slug>/photos/{instagram,maps}/` (Instagram/Maps are never scraped by default; `scrape.py` is an explicit opt-in, see below), calls Claude via forced tool use in `llm.py` (schemas live there). Each stage caches JSON in `data/leads/<slug>/profile/`; `--refresh` ignores it. `store.py` owns the `lead_status`/`lead_profile` tables and the slug/folder layout. `enrich.finish()` (shared by `enrich.py` and `ingest.py`) stores the profile in `lead_profile` (its `brief_path` column is a leftover and stays NULL) and moves the lead to `enriched`; the web app is the only place the analysis is read. The optional `development_direction` key of the profile (`llm.DEV_SCHEMA`: pages, features, stack, SEO, phases, outreach) feeds the Build plan tab; keep it optional so older profiles still validate. The stack is fixed for every site (`config.SITE_STACK`: Next.js + Tailwind CSS): both analysis prompts and the `tech_stack` schema description say so, and `server/sitestack.py` rewrites `tech_stack` when a lead is read (framework/styling rows replaced, the rest kept), so older profiles agree in the tab and the downloads without touching their files. Change the stack in `config.py` only. All profile/presence/menu text is untrusted: the UI renders it as text (see the `ui/` note). `research.py` adds a free `competitors()` (neighbors within `COMPETITOR_RADIUS_M`, from `places`+`audits`) and `presence()`, which uses `llm.research_presence` (Anthropic server-side `web_search` tool; handles `pause_turn` continuation) then `llm.extract_presence` (forced-tool structured output with an operating-status verdict). Both feed `llm.synthesize`; `score.py` surfaces the verdict as the `operating_status` CSV column. Web-search findings are lower precision than official APIs (Google Places / TripAdvisor Content API were deliberately not used).

## Web app

- `app.py` runs uvicorn on `127.0.0.1:config.UI_PORT`. `server/__init__.py` chdirs to the repo root because the pipeline's paths are cwd-relative.
- `server/app.py` — Starlette routes: JSON under `/api`, everything else serves `ui/dist` with an SPA fallback. `server/leads.py` builds the read models (`list_leads` from `score.ranked()`, `lead_detail`, `block()` = neighbours positioned in metres for the plot). `server/outreach.py` owns the private note and contact log (`lead_notes`, `lead_contacts`, created in `store.connect()`); logging a contact sets `contacted`, an opt-out sets `rejected`. `server/files.py` is the only way the UI touches lead folders: fixed groups (`instagram`, `maps`, `menu`, read-only `site`), bare file names only, uploads verified with Pillow, removal moves to `data/leads/<slug>/.trash/`. Downloads: `GET .../files/<kind>/<name>?download=1` sends the original as an attachment, and `GET /api/leads/<key>/files.zip[?kind=...]` zips one group (or all, one folder each) via `files.archive()`; both are read-only and include the `site` group.
- `server/buildplan.py` renders a lead's `development_direction` (plus identity, visual identity, design direction, menu and low-confidence fields) as a Markdown brief for a design/coding agent; `GET /api/leads/<key>/build-plan.md` downloads it (404 until the lead has a plan) from the "Download brief" button on the Build plan tab. It leaves out outreach, pitch hooks and next steps on purpose, tells the reader the text is untrusted, and reads every model-written field defensively (`tests/test_buildplan.py`). When the lead has a design system its "How to use" section points at the design-system file.
- `server/designsystem.py` renders `profile/design_system.json` (`llm.DESIGN_SYSTEM_SCHEMA`, shown on the Design system tab, `ui/src/components/lead/design.tsx`) as the companion Markdown file; `GET /api/leads/<key>/design-system.md` downloads it (404 until the lead has one). The design system is a separate optional output of the same `claude -p` run (`enrich_job.OUTPUTS`, step 7 of `server/prompts/analyze.md`), not part of `development_direction`; the API-key `enrich.py` path does not produce it. For a lead that is already researched, the Design system tab's button runs `enrich_job.start_design` (`POST /api/leads/<key>/design-system`, same `enrich` lane, prompt `server/prompts/design.md`): it stages the finished profile, menu and photos, does no web research, and saves only `design_system.json` (no ingest, the profile is untouched). The design rules both prompts share live in `server/prompts/design_rules.md` (`{design_rules}`). `app.py` loads prompts and `OUTPUTS` at import, so a running app must be restarted after changes here, or a "Research again" would not write a design system. It is written for the fixed site stack (`config.SITE_STACK`, Next.js + Tailwind CSS v4) and a test fails if that changes: the file carries a Tailwind `@theme` block (palette reset with `--color-*: initial`, `--text-*` with line-height/weight companions, `--container-site`, `--radius-brand`, fonts in `@theme inline`), `app/fonts.ts` for `next/font/google` (family `Source Sans 3` -> `Source_Sans_3`, variable `--font-<role>-src`), a root `app/layout.tsx`, and per-component Tailwind `classes`. That code is generated from validated values, never copied from model text: `ingest.problems` enforces the schema `pattern`s (so a bad value gets the repair round) and the renderer re-checks them with the same `llm.*_RE`; contrast ratios are computed there, never taken from the model. `tests/test_designsystem.py` compiles the exported theme with the repo's own Tailwind (skipped without node and `ui/node_modules`). `server/mdutil.py` holds the escaping helpers both Markdown exports share (`tests/test_designsystem.py`).
- `server/security.py` — the API can spawn processes, so it only answers Host 127.0.0.1/localhost and every non-GET needs the `X-Leads-UI: 1` header and an allowed Origin (`UI_PORT`, `UI_DEV_PORT`). Keep GETs free of side effects.
- `server/jobs.py` — pipeline stages run as subprocesses (`sys.executable -u`, UTF-8) so `sys.exit`, print-based progress and `audit._PS` stay isolated and jobs can be cancelled (`taskkill /T`). `POST /api/jobs/maintenance {task}` (`jobs.MAINTENANCE`: `find_sites`=`audit.py --discover`, `pagespeed`=`--perf`, `rescore`=`--rescore`, `backfill`=`quality.py --backfill`) backs the buttons on the Pipeline page; add new one-shot CLI stages there. Two lanes: `pipeline` (serial queue: discover, audit, single-place audit, re-render) and `enrich` (one at a time, 409 if busy). Logs are polled by cursor (`GET /api/jobs/<id>?after=seq`) and persisted in `data/runs/<job_id>/`.
- `server/enrich_job.py` + `server/claude_cli.py` — "Get insights": prepare (approve if no status) → `enrich.py --collect-only --refresh` → stage a copy of that lead's inputs into `data/runs/<id>/ws` → `claude -p` there → validate `out/{profile,menu,presence}.json` with `ingest.check_file` (one repair round via `--resume`) → back up the old profile to `data/runs/<id>/prev`, copy the new files in → `ingest.py`. The Claude run is treated as steerable by untrusted web content, so containment is structural: `--restricted --safe-mode --strict-mcp-config --disable-slash-commands`, tools limited to Read/Glob/Grep/Write/WebSearch/WebFetch, `dontAsk` with no prompts, an environment allowlist (no `ANTHROPIC_*`/`CLAUDE_CODE_*`), and an init gate that kills the run if it starts with other tools, MCP servers or an API key. Do not add Bash or widen the workspace. The prompt is `server/prompts/analyze.md`.
- `ui/` — Vite + React + TypeScript + Tailwind v4 + shadcn/ui (Base UI flavour: custom triggers use `render`, not `asChild`). Routes: `/` (ranked sheet, filters in the URL), `/leads/:key`, `/board`, `/pipeline`. A lead's URL key is `store.key()` (`osm-node-123`) because place ids contain `:` and `/`. Data via SWR hooks in `ui/src/hooks/use-data.ts`; API types in `ui/src/lib/types.ts` are hand-written and must follow `server/leads.py`. Analysis text is model-written: render it as text, link only through `<Ext>` (http/https only), no `dangerouslySetInnerHTML`.
- Design: `PRODUCT.md` (what the app is for) and `DESIGN.md` (the "Plano Catastral" visual system: survey-plan lettering, zoning colours for tiers, blue as the only live-state colour, the score as a parcel strip). Follow them for UI changes; the project's `.claude/skills` (shadcn, impeccable, vercel-react-best-practices) are the expected way to work on `ui/`.

## Audit data quality

- `sitesignals.py` parses a page with BeautifulSoup (links, headings, head, visible text, JSON-LD). A signal it cannot judge on a JavaScript-rendered page is `None`, not 0; `audit.web_score()` leaves unknown signals (including an unmeasured PageSpeed) out of both earned and available points, so they are neither rewarded nor penalised.
- `urlcheck.check()` returns the fetched `response` for `ok` pages and `audit_site()` reuses it (one fetch per site). `match_place()` decides `name_match` from name words, the listed phone and locality words; one shared word of several is `None` (unverified), not a match.
- `audits` has `confidence` (high/medium/low), `evidence`, `js_shell`, `url_source` (`osm`|`discovered`). `audit.init()` adds them to old DBs with `ALTER TABLE`; `save_audit` inserts by column name. `score.py` multiplies Need by `config.CONFIDENCE_NEED_FACTOR`, so unverified "no website" ranks below verified-broken sites; a loaded page whose `name_match` is 0 gets Need of at least 60% of the weight.
- `sitefind.py` (`--discover`): derives domains from the name, fetches only hosts that resolve, and accepts a page only if the phone is on it or name matches and the page mentions the area. A hit is stored as a normal `website` audit with `url_source='discovered'`; `places.website` is untouched and rechecks read the URL from `url_checks`.

## Things that span files

- **The `places` schema is a Google Places superset** (rating, review_count, price_level, reviews_json, types) left over from an earlier Places-API version. With OSM data those columns are NULL, so `score.py` branches on `rich = rating and review_count present`: the rich path uses the original formula and `TIER_A/B` (80/60); the OSM path uses completeness proxies and the lower `OSM_TIER_A/B` (70/50) defined in `score.py`, not `config.py`. Keep both paths working when changing either side.
- The `places` and `audits` tables use positional inserts (`"?" * 19` in `discover.py`, 23 placeholders in `audit.py`); adding a column means updating the `CREATE TABLE`, the tuple, and the placeholder count together. Existing `leads.db` files won't pick up schema changes (`CREATE TABLE IF NOT EXISTS`).
- `audit.py` skips places already audited, except websites whose `url_checks.status != 'ok'` and whose check is older than `config.URL_RECHECK_DAYS` (and ones audited before `url_checks` existed); `--refresh` redoes all. Dead/unreachable/parked URLs score like "no website" in `score.py`; `blocked` gets a neutral web score. `enrich.py` only crawls sites whose audit has `http_ok`, so broken/blocked ones are skipped. `discover.py` re-runs overwrite place rows by id.
- `config.QUERIES`, `GRID_STEP_M`, `TILE_RADIUS_M`, and `MIN_REVIEWS` (only applies to rich data) are mostly vestigial from the Places version; `discover.py` currently uses a single circular Overpass query per area.
- OSM coverage in Colombia is patchy, so "no website" can be a data gap; the README advises verifying before outreach. Overpass is a shared service, so run one area at a time.
